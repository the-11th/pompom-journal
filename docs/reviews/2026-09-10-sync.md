# Synchronization review — 10 September 2026

Scope: Android journal/task outboxes, media and location transfers, Flask mobile APIs, offline edits, acknowledgements, and concurrent changes. All fixtures use temporary stores and the separate QA application. No production credentials or phone journal data were used.

Provider API/OAuth and Discord transport behavior was checked with synthetic responses, including failures and concurrency. It was not verified against live connected services. USB pairing/update scripts used fake ADB; device checks installed only the separate QA package.

## Corrected findings

### Durable writes and acknowledgements

- TaskOutbox locked each instance independently. The device regression retained only **7 of 48** simultaneous writes before the fix and **48 of 48** after sharing its lock across instances.
- Corrupt task outbox JSON was silently treated as empty. It now retains a recovery copy and reports an actionable failure.
- Valid JSON containing malformed individual task, journal or media records was also silently skipped. **59 failing runtime cases** now preserve original bytes and recovery backups across reads, acknowledgements and later writes. Optional legacy journal fields remain compatible; missing draft request IDs/local timestamps are migrated once durably, preventing a fresh identity on every read.
- Blank drafts of existing journal entries could be replaced by a pull, undoing an intentional clear. Pull policy now treats the clear as a pending edit.
- Journal typing reused an in-flight request identity. Draft saves generate a fresh request identity and local revision; acknowledgements compare content as well as identity and preserve newer typing.
- Task pulls had a check/request/write race. Cache replacement rechecks the durable outbox and expected cached version under the shared lock.
- Task server normalization could leave subsequent queued edits based on untrimmed text. Acknowledgements now rebase only acknowledged fields and preserve later phone edits; the worker rereads each queued mutation after earlier acknowledgements.

### Task conflict preservation

- Native task saves now send only fields changed from the captured editor snapshot, with optional baseline values and status. Unrelated Mac changes merge; overlapping changes return durable conflicts.
- Versioned deletes compare the complete editable baseline, avoiding deletion of unseen Mac changes. Clients without the optional baseline retain legacy behavior.
- Task detail HTTP endpoints now reject non-object JSON, missing/non-string text and boolean/fractional reorder indices before writes. **41 malformed-input cases** preserve exact file bytes; 29 initially failed through crashes, silent note clearing or index coercion.
- Completed task notes previously returned success without applying the edit. The API now reports a conflict with the current task.
- Conflicts block later changes to the same task and never automatically retry. Explicit review can keep phone fields, use the Mac version, reopen a completed task, or save a one-off copy of an expired/deleted task.
- Expired history is retained. Copy task IDs and request IDs stay stable on retry; a repeated resolution cannot create another copy.

### Journal and provider updates

- Transcript-only entries now count as content and save normally.
- Config distinguishes meaningful entry dates from all occupied dates. Cleared existing entries are downloaded as clears instead of being mistaken for remote deletion.
- Google sync includes an explicitly opened historical date and refreshes today's existing sleep. RescueTime refreshes today's partial totals; explicit force refreshes old cached summaries. All provider routes forward `force=1` and validate focus dates.
- Failed provider days no longer advance the success timestamp. RescueTime keeps previously saved activity detail when only its fresh detail request fails.
- Background provider updates previously caused false journal conflicts by changing `updated`. Responses now project an opaque editable-content revision. It covers title/body/mood/transcript/document/tags and unmanaged numbers, including archived user data, while excluding provider fields and timestamps.
- Optional editable revision checks accept provider-only refreshes, reject real concurrent edits even with equal timestamps, preserve managed numbers, and reject recreation of a deleted nonempty entry. Legacy clients still use timestamp checks.
- Native drafts retain the server revision internally through persistence, conflict choices, and acknowledgements. The WebView continues using local timestamps for local edits.
- Native journal conflict choices optionally check both the displayed local timestamp and complete displayed Mac snapshot under the journal lock. New phone typing, changed Mac data even with the same timestamp, and repeated already-resolved choices are rejected before writes. Hidden archived tags, provider/archived numbers and omitted transcript survive both ordinary saves and explicit resolution.
- Frozen/coarse clock ticks and a clock rollback could reuse local journal editor revisions. Four focused unit failures now pass: revisions advance monotonically for local typing, command acknowledgements and changed remote pulls, while unchanged provider updates retain the open editor baseline.
- A provider-only remote pull now retains the native local editor revision when the editable hash matches. Real content changes invalidate it, including same-timestamp changes. Unit and runtime checks cover the distinction.
- Spotify refresh now preserves the refresh token when a response omits it, and provider token expiry uses the injected clock.
- Google metric refresh removes obsolete sleep-stage numbers after a result changes to classic sleep, without touching manual numbers or another provider's metrics.
- Slow provider requests held the global store lock: all three providers blocked concurrent saves and disconnects for at least the one-second test window. Fetching now operates on snapshots outside that lock in the zero-Flask `provider_sync.py`; reconciliation applies only provider-owned fields to the latest stores. Twelve concurrent cases cover save, disconnect, credential replacement, and deletion for each provider. Local operations complete before the synthetic provider is released. Existing OAuth callback lock scope remains unchanged.
- Spotify's separate analytics snapshot endpoint erased any section whose fetch failed, advanced the daily music sync timestamp, and blocked local saves/disconnects. Thirteen failing cases now pass: successful sections refresh, failed sections retain their previous values, partial errors retain the previous full-snapshot time, and analytics refresh never delays daily play sync. Token refresh errors return the saved snapshot rather than 500. Two additional checks preserve exact file bytes when every section fails and protect a newer section during reconciliation.

### History import retention

- Importing the same Spotify JSON file twice doubled 2 tracks to 4; overlapping files produced 5 instead of 3. Imports now validate the whole batch, then merge exact per-play receipts before one atomic journal save. Repeated and renamed files, reversed row order, repeated rows and overlapping files are idempotent after reopening the store. Invalid later rows or corrupt saved receipts leave all earlier dates and file bytes unchanged. ZIP files receive a clear instruction to extract and choose JSON; ZIP support was not added.
- Each imported day stores `music_history` with SHA256 identities and full aggregate counters. Displayed `music` contains the concise summary and `source: history_import`. The pre-import snapshot is retained unchanged as `music_legacy`; later API snapshots go to `music_live`. Neither is added to receipt-backed totals. Import-covered days therefore show only their imported history totals, including when an import arrives during an API request. Live data remains saved separately; no approximate matching between API and export timestamps is attempted.
- Entry and analytics UI label those dates **Imported history** and explain: “Imported days use history totals. Live sync stays saved separately.” Analytics exports retain source metadata; mobile/web entry responses omit internal receipts and retained snapshots. This is a covered-day policy: later live plays on an imported date are retained but not added to its displayed history total. Standard and extended export formats can identify a play differently when one lacks a track URI; deduplication guarantees exact normalized identities, not approximate cross-format matching. Export timestamps retain their documented UTC day grouping. [Spotify data reference](https://support.spotify.com/in-en/article/understanding-your-data/).
- Durations accumulate in milliseconds before rounding; artist/track counters retain values beyond the displayed top list so later imports can change ranks correctly. A 100,000-play synthetic benchmark spanning 209 days parsed in 0.137 s, merged in 0.281 s, and replayed reversed after reopening in 0.317 s with unchanged data. The JSON store was 11.923 MiB; whole-process peak was 216.5 MiB while holding raw, parsed, serialized and reopened copies. This remains JSON storage with whole-file writes; large imports add durable receipt volume.

### Transport and tracking

- USB helper provisioning overwrote Google credentials saved after its initial store read. A controlled shell/Flask regression reproduced the lost update. Provisioning now uses the existing server transaction; the helper only writes its token cache. Valid tokens remain stable, revoked tokens rotate, failed requests preserve both stores and never start pairing. JSON-only, literal-loopback, foreign/null Origin, cross-site Fetch Metadata and forged-forwarded-address tests pass. An additional concurrent server test preserves provider settings and both returned credentials.
- The watcher now targets one selected physical device, excludes emulators by default, and retries a failed start while the cable remains connected. The updater previously uninstalled after any replacement-install failure; it now permits signature migration only for an explicit signature mismatch naming the production package. Storage, offline-device, downgrade, malformed APK, unknown signature errors, another package, and a misleading filename retain the installed app. These checks use fake ADB and synthetic backups; no live update or pairing was performed.
- Two synthetic recovery filenames reproduced a later migration failure after the old app was already uninstalled. Backup extraction and complete filename checks now run before uninstall; unsupported colon/newline paths retain the installed app and the persistent recovery archive. File traversal uses NUL delimiters so an embedded newline cannot evade the check.
- No-due task creation sent the string `null`; it now sends JSON null.
- HTTP redirects are disabled. Temporary HTML errors and malformed/partial successful responses stay retryable; incomplete config/task lists cannot clear caches.
- Successful task responses must include valid task content and the expected identity. Malformed creation acknowledgements and wrong task IDs cannot acknowledge away a queued edit.
- A later transport pass reproduced **26** unsafe successful/conflict responses on Samsung. Task deletion and tag writes now require literal `ok: true`; 409 journal/task snapshots use the same identity/content validation as successful replies. Unreadable, partial, wrong-date and wrong-ID conflicts stay retryable. Explicit null remote records still offer deletion recovery, and the earlier journal `entry` conflict envelope remains compatible. All 26 cases now pass.
- Journal GET/ACK parsing now validates required fields, requested date, tags/numbers/mood and document shape before accepting a response. Seven runtime cases initially accepted incomplete or wrongly dated replies; all now remain retryable with the saved draft intact.
- The USB worker incorrectly required an internet-connected Android network. A device test reproduced this; the constraint is removed because ADB reverse uses loopback. Failed sockets keep durable edits queued with exponential backoff.
- Tracking starts only after explicit enable and precise permission. An unset preference stays off, matching the documented behavior. Existing device checks verify enabled resume and disabled persistence.
- Failed pairing no longer claims the phone and Mac matched when nothing was transferred. Existing error punctuation is retained without adding another period.
- Discord inbox pulls require an explicit successful acknowledgement before advancing their success time. Malformed or negative HTTP-200 replies keep locally saved messages and report a retry. Lost-ACK replay preserves local message captions and hidden state. Replacing the receiver token/application identity during a pull cannot mark the new connection synced.
- Phone/health push parsing no longer crashes on infinite numeric values or creates separate entries under unpadded dates. Invalid heart-rate clock times are skipped. Requests with no valid days return400 without changing journal bytes or the last successful sync time. Thirty-four failing cases now pass; valid legacy normalization remains intact.
- Android usage upload validates every acknowledged date instead of trusting HTTP2xx. Seven malformed/partial response cases retry, and synthetic collection guards stop before a denied read or after access is revoked mid-read. Android requires usage access and may return no data before user unlock; the worker checks both states. [Android UsageStatsManager reference](https://developer.android.com/reference/android/app/usage/UsageStatsManager). File/map and media-conflict counts now use singular wording for one item.

### Media queues and binary transfers

- A queue of 501 distinct metadata edits previously failed forever against the server's 500-change limit. Android now sends bounded batches; 500+1 succeeds.
- Media conflict persistence moved into the guarded merge. Other successful batches retain an unresolved conflict, while a response from before an explicit choice cannot resurrect the resolved conflict.
- Conflicts are excluded from automatic resends; resolving one schedules a sync. New metadata arriving during a worker run triggers a subsequent retry.
- A delayed full-state response could remove a newer settled record. Revision-aware merging preserves newer records; media deletions remain archived records with revisions.
- Lost responses after the server commits either batch retain pending operations and replay receipts without applying metadata twice.
- Synthetic binary tests cover truncated bodies, cable interruption, correct byte-range resume, incorrect range rejection, a server ignoring Range, checksum failure and retry, and no repeated transfer after receipt persistence.
- A map with a mismatched manifest size was incorrectly reported as transferred. Size must now match before the final file and receipt become available.
- Android hid a verified downloaded map as soon as replacement metadata arrived. Truncation, cable loss and checksum-failure regressions reproduced it. Cached metadata now stays on the previous verified pack until replacement publication; a two-pack test retains the completed first update independently when the second fails, then resumes only the second. Genuine remote identity removal still removes its listing. All replacement cases pass on Samsung.
- Both byte-serving adapters now reject an outdated `?v=` checksum with409/`map_version_changed`, preserving requests without a version. The checksum check and opening of the byte stream share the map publication lock. A deterministic Flask race holds a waiting replacement until the old reader opens, then verifies that reader receives only its original archive; native runtime coverage also checks already-open streams survive atomic replacement. Shared rendering refreshes a stale manifest once per obsolete URL and keeps canvas position.
- Map region creation accepts an optional stable caller ID. Identical retries return the existing normalized region without a write or download; changed data under the same ID rejects. Missing/unknown map actions no longer fall through to download.
- Offline metadata validation accepted 15 invalid place/group cases on Android. Names, Unicode length, coordinates, radius, colors and editable-field rules are now checked before any batch write. Invalid batches leave state and outbox unchanged; valid partial edits and normalized group tags are preserved.
- Shared metadata refresh/mutation responses now merge by server record revision. Delayed replies cannot undo newer names or archives, while imported assets and default groups remain visible even without a global revision increment. Android snapshots use a separate persisted local revision because optimistic record revisions can fall when coalesced edits receive one server ACK. Equal-clock native responses retain separately imported assets. Six async response-order regressions and eleven real browser photo-control flows pass.
- Coalesced metadata ACKs now normalize optimistic phone revisions to the accepted server revision. A delayed duplicate ACK cannot undo a later settled edit. The next edit after sync is tested against the actual server revision.
- Native media conflicts expose an opaque reviewed-version hash. Optional expected_revision guards reject an unseen phone/Mac version or already-resolved choice with409/current before changing state or queued work; older clients remain compatible.
- Additional field checks reproduced eleven malformed metadata batches accepted by the server and thirteen by Android, including string booleans, invalid message dates/captions and invalid native photo timestamps. Validation now rejects these editable fields before any item in the batch is persisted; old stored metadata remains readable. The full Samsung QA suite passes after the fix, including WebView photo and map interactions.
- Photo tag batch saves now share the stable mutation-attempt cache. A lost successful response retries the identical operation IDs; web/native async regressions and an actual photo-dialog Save retry verify one write with the caption retained.
- Native metadata responses are validated before merge: all sent operations must be acknowledged or explicitly conflicted, accepted IDs must belong to the request, acknowledged records must exist, and record identity/revision/shape must be valid. Nine malformed successful replies were previously accepted, including one that removed its acknowledged local record and pending edit.
- Tracking day manifests optionally include an observation count; the cache preserves it through external changes and compression. Downloads reject wrong-day/naive timestamps, duplicate IDs, invalid coordinates/accuracy, non-object rows and count mismatches before writing observations or remote hashes. Upload receipts require exactly the sent IDs and explicit success. Eleven malformed-response cases now pass; counted and legacy manifests both skip unchanged received days.
- Preview responses now validate the complete Content-Range even when the requested offset is zero. Four malformed 206 cases previously published incomplete previews. Whole map manifests are validated before replacing cached pack metadata; seven malformed manifest cases previously changed that cache before failing. All eleven cases now pass on the Samsung QA app, alongside correct resume, ignored Range restart and checksum retries.

## Tracking performance

- At 10,000 synthetic observations/day, uncached tracking manifest requests blocked a concurrent journal request for **0.315 s at 70,000 samples** and **1.281 s at 300,000**. Append requests blocked it for **0.205 s** and **0.890 s**; the append benchmark reached **399.5 MiB** peak process RSS.
- A bounded cache holds at most 2,048 small daily receipt/fingerprint pairs across stores, without caching observation rows or changing authoritative JSON/gzip formats. File device/inode/size/mtime_ns/ctime_ns detect external replacements and in-place writes. Regression coverage includes deletion/recreation, plain↔gzip migration, interrupted duplicate formats, corruption backup/recovery, independent returned objects and eviction.
- The isolated 300,000-sample benchmark improved from **0.842 s cold** to **0.00047 s warm** (35.5 MiB peak RSS). Cold scans and immutable-ID append checks still scan history.
- Append indexing remains a proposal: bounded per-day membership filters could cheaply exclude new IDs while exact row comparisons verify possible duplicates. It needs duplicate-heavy batch benchmarks and cross-process writer locking before adoption; no immutable-ID guarantees were weakened.

## Remaining limits

- Live provider authorization, receiver hosting and real USB pairing/update behavior require the user's connected services. This review used fake transports and a separate installed QA application.
- Large JSON stores still use whole-file writes. Tracking append validation retains its existing full-history scan; the measured cache accelerates manifests, not every append.
- Receipt-backed music covers the imported UTC dates. Exact normalized identities deduplicate repeat files; no approximate matching joins standard exports, extended exports and live API timestamps. Retained live and legacy snapshots are preserved separately.
- Successful task/journal request receipts retain the existing newest-200-per-device policy. Modern task client IDs and journal conflict checks protect data after receipt eviction; very old retries can require explicit review rather than replaying the original response.
- Original files and map packs use checksums. Generated photo previews without a checksum rely on transfer length/range validation; those checks cannot detect every possible same-length content corruption.
- Store transaction locks protect this single server process. The tracking manifest cache detects external file changes, but this review did not add cross-process write transactions or a database.
